Circuit breaker: the generation number edge case

Question: what is the generation number edge case?

Status: fixed. The generation-number fix and HTTP timeouts are implemented in CircuitBreaker.java and SimplePriceService.java, with tests for both cases below. The first half of this page describes the problem as it was before the fix. The other review fixes (client errors, missing prices, product-name checks, cart validation and rounding up) are near the end of the page.

The edge case is stale results. A call gets permission while the breaker is in one state, but reports its success or failure after the breaker has moved to another state. The breaker can't tell old results from current ones, so a late result can override the decision the half-open trial is supposed to make.

Why it can happen

Before the fix, recordSuccess() and recordFailure() took no arguments. They always acted on the breaker's current state, however long ago the caller got permission:

public synchronized void recordSuccess() {
    failureCount = 0;
    state = State.CLOSED;              // closes the circuit no matter who reports it
    halfOpenRequestInProgress = false;
}

Under Option B, a call that got ALLOWED can take a while: up to 3 attempts plus 2 × 200 ms of sleep. fetchPrice() also had no HTTP timeouts (bug 5 in the review), so one hanging attempt could last minutes. Meanwhile, other threads can open the circuit and start a half-open trial.

The fix (implemented): a generation number

The breaker has a counter that goes up on every state change. Each permission is a Permit carrying the generation it was granted in, and results from an older generation are ignored.

src/main/java/org/designprinciple/CircuitBreaker.java

public static final class Permit {
    private final Permission type;      // REJECTED, ALLOWED or TRIAL
    private final long generation;      // breaker state the permit was granted in
    ...
    public Permission getType() { return type; }
}

// Incremented on every state change; permits from an older generation are stale
private long generation = 0;

public synchronized Permit acquirePermission() {
    if (state == State.OPEN) {
        if (System.currentTimeMillis() - openedAt > retryTimeout) {
            transitionTo(State.HALF_OPEN);
        } else {
            return permit(Permission.REJECTED);
        }
    }
    if (state == State.HALF_OPEN) {
        if (!halfOpenRequestInProgress) {
            halfOpenRequestInProgress = true;
            return permit(Permission.TRIAL);
        } else {
            return permit(Permission.REJECTED);
        }
    }
    return permit(Permission.ALLOWED);
}

public synchronized void recordSuccess(Permit permit) {
    if (isStale(permit)) {
        return;
    }
    if (state == State.HALF_OPEN) {
        transitionTo(State.CLOSED); // trial succeeded
    } else {
        // CLOSED: stay in the same generation so other in-flight calls still count
        failureCount = 0;
    }
}

public synchronized void recordFailure(Permit permit) {
    if (isStale(permit)) {
        return;
    }
    // Trial failed OR threshold reached → OPEN
    if (state == State.HALF_OPEN || ++failureCount >= failureThreshold) {
        openedAt = System.currentTimeMillis();
        transitionTo(State.OPEN);
    }
}

// Results from a REJECTED permit or from an earlier state are ignored
private boolean isStale(Permit permit) {
    return permit.type == Permission.REJECTED || permit.generation != generation;
}

private void transitionTo(State newState) {
    state = newState;
    generation++;
    failureCount = 0;
    halfOpenRequestInProgress = false;
}

SimplePriceService keeps the Permit it receives and passes it back when it records the result:

src/main/java/org/service/SimplePriceService.java

CircuitBreaker.Permit permit = circuitBreaker.acquirePermission();

if (permit.getType() == CircuitBreaker.Permission.REJECTED) {
    throw new RuntimeException("Circuit is OPEN / HALF_OPEN busy. Skipping API call");
}

int maxAttempts = permit.getType() == CircuitBreaker.Permission.TRIAL ? 1 : MAX_RETRIES;
...
circuitBreaker.recordSuccess(permit);   // on success
...
circuitBreaker.recordFailure(permit);   // after all attempts fail

Design decisions worth remembering

  • A success while CLOSED does not bump the generation. It only resets failureCount. If it bumped the generation, every other call in flight at the same time would become stale and its failures would be lost.
  • The OPEN timeout counts from when the circuit opened (openedAt), not from the last failure. Previously lastFailureTime was updated by every failure, so late failures kept restarting the 5-second countdown.
  • Results from REJECTED permits are ignored, so a caller that was refused can't change the breaker's state.
  • The no-argument recordSuccess() / recordFailure() were removed. Keeping them would leave the old loophole open.
  • allowRequest() was removed. It called acquirePermission() and threw the permit away. In HALF_OPEN that claimed the trial with no way to report a result, leaving the breaker stuck in HALF_OPEN for good. Each request now gets exactly one Permit, shared by all its retry attempts, and records exactly one result with it.

How the two cases play out now

  • Case 1: D's permit is from generation 0 (CLOSED). The circuit is now in generation 2 (OPEN was 1, HALF_OPEN is 2). D's recordSuccess() is ignored, and only E's trial result can close or re-open the circuit.
  • Case 2: D's recordFailure() is ignored, the flag stays true, and F gets REJECTED. Only one trial exists at a time.

HTTP timeouts (implemented)

Most of the danger came from calls that could hang forever. Connect and read timeouts limit how long a stale call can stay in flight.

src/main/java/org/service/SimplePriceService.java

// Without timeouts a hanging connection blocks the caller forever
private static final int CONNECT_TIMEOUT_MS = 2000;
private static final int READ_TIMEOUT_MS = 3000;

protected BigDecimal fetchPrice(String product) throws Exception {
    URL url = new URL(baseUrl + product + ".json");
    HttpURLConnection conn = (HttpURLConnection) url.openConnection();
    conn.setRequestMethod("GET");
    conn.setConnectTimeout(connectTimeoutMs);
    conn.setReadTimeout(readTimeoutMs);

    try {
        int status = conn.getResponseCode();
        ...   // status and price checks, see "Other fixes from the review" below
    } finally {
        conn.disconnect();
    }
}
  • A hanging attempt now fails within about 5 seconds (2 s connect + 3 s read) with SocketTimeoutException.
  • The reader is closed with try-with-resources and the connection is always disconnected, so nothing leaks when a call fails.
  • A package-private constructor takes the base URL and timeouts so tests can use a local server. The cast is now to HttpURLConnection (the real HTTPS URL still works).

Explained: permit.generation != generation

private boolean isStale(Permit permit) {
    return permit.type == Permission.REJECTED || permit.generation != generation;
}

What the expression compares

permit.generation != generation compares two numbers:

ExpressionWhat it isSet when
permit.generationThe generation stamped on the permitOnce, when the request called acquirePermission(). It's final, so it never changes
generation (short for this.generation)The breaker's current generationIncreased by transitionTo() on every state change

Put simply, the check asks: "Has the breaker changed state since this request got its permission?"

  • Equal: the breaker is in the same state the request was given permission in. The result is current and gets applied.
  • Not equal: the breaker has changed state at least once while the request was running. The result is stale, so isStale() returns true and recordSuccess()/recordFailure() return without doing anything.

The permit is like a ticket dated with the breaker's state when it was issued. A result is only accepted if that state is still the current one.

Worked example (Case 1)

Breaker (1, 100), so one failure opens it:

StepCodegenerationPermit getsCheck result
1D: acquirePermission() while CLOSED0D = (ALLOWED, 0)
2A: acquirePermission() while CLOSED0A = (ALLOWED, 0)
3A: recordFailure(A)00 != 0 is false, so applied: CLOSED → OPEN, generation becomes 1
4100 ms later, E: acquirePermission()1, then 2E = (TRIAL, 2)OPEN → HALF_OPEN happened inside this call
5D (slow) finishes: recordSuccess(D)20 != 2 is true, so stale and ignored. The circuit stays HALF_OPEN
6E finishes: recordFailure(E)22 != 2 is false, so applied: HALF_OPEN → OPEN, generation becomes 3

D and E report results only a moment apart, but only E's counts, because only E's permit matches the breaker's current state.

Why != and not <

A permit's generation can never be higher than the current one, because the counter only goes up. So != and < give the same answer here. != states the intent more directly ("same state or not"), and it keeps working if the counter overflows and wraps round to a negative number. < would get that wrong.

Why requests in the same CLOSED period still count

Successes and failures that stay below the threshold don't call transitionTo(), so they don't change the generation. A and D in steps 1–2 both have generation 0. If A's failure hadn't reached the threshold, D's result would still be applied. That's how failures from requests running at the same time add up to the threshold.

Java details

  • generation with no prefix means this.generation, the field of the CircuitBreaker that owns the method. Permit also has a field called generation, but this code runs in CircuitBreaker, so the plain name refers to the breaker's field.
  • permit.generation is private in Permit, yet CircuitBreaker can read it. Java allows this because Permit is nested inside CircuitBreaker, so the outer class can see the nested class's private members. Code outside CircuitBreaker can't read or fake a permit's generation, and the Permit constructor is private too, so only the breaker can create permits.
  • Thread safety: isStale() is only called from recordSuccess() and recordFailure(), which are synchronized. Reading generation and any state change based on it happen under the same lock. That means transitionTo() can't run on another thread in the middle of a check.

Will the generation keep increasing?

Yes, it only ever goes up. But it goes up slowly, it can't realistically overflow, and nothing would break even if it did.

When it increases

generation++ lives only in transitionTo(), so it goes up on state changes, not on requests:

EventChangeGeneration
Normal requests in CLOSED, whether they succeed or fail below the thresholdnoneunchanged
Threshold reachedCLOSED → OPEN+1
Requests while OPEN (rejected)noneunchanged
First request after the timeoutOPEN → HALF_OPEN+1
Trial succeedsHALF_OPEN → CLOSED+1
Trial failsHALF_OPEN → OPEN+1

A healthy service never changes the generation, however many millions of requests it serves. It only moves when the price API is failing.

How fast it can grow

Every OPEN period lasts at least retryTimeout (5 s) before moving to HALF_OPEN. So even if the API fails constantly, the fastest pattern is about 2 increments per 5 seconds (OPEN → HALF_OPEN → OPEN → …). At most that's about 3 increments every 5 seconds.

generation is a long, so it can reach Long.MAX_VALUE ≈ 9.2 × 1018:

  • At the real maximum (about 0.6 increments per second), reaching that would take hundreds of billions of years.
  • Even with a billion state changes per second, it would take about 292 years.

The counter is also a single long field, so it uses 8 bytes no matter how high it gets. It starts again from 0 when the breaker is recreated, for example when the app restarts.

Even an overflow would be harmless

If it did overflow, Java would wrap it from Long.MAX_VALUE to Long.MIN_VALUE without throwing. The breaker only checks whether two generations are equal:

permit.generation != generation

It never checks which one is larger, so wrapping doesn't affect the logic. A stale permit would only be wrongly accepted if a request stayed in flight for exactly 264 state changes, which is impossible.

No change is needed. Even an int (about 2.1 billion) would last over 100 years at the real maximum rate, but long takes the question off the table.

Other fixes from the review (implemented)

These fix review issues 3 to 7. Issue 5's timeouts and connection clean-up are covered in the "HTTP timeouts" section above.

3. Client errors no longer retry or open the circuit

Before: an unknown product returned 404, which was retried 3 times and counted as a breaker failure. Enough of them opened the circuit, and then valid products failed too.

src/main/java/org/service/PriceClientException.java (new)

/**
 * The price API rejected the request itself (HTTP 4xx, e.g. unknown product).
 * Retrying won't help and the service isn't failing, so this is not retried
 * and does not count towards the circuit breaker.
 */
public class PriceClientException extends RuntimeException {
    private final int status;
    ...
}

src/main/java/org/service/SimplePriceService.java

// in fetchPrice()
if (isClientError(status)) {
    throw new PriceClientException(
            "Price request rejected for product " + product + ", HTTP status: " + status, status);
}
if (status != 200) {
    throw new RuntimeException("Failed with HTTP status: " + status);
}

// 408 (timeout) and 429 (rate limited) are 4xx but temporary, so they stay retryable
private static boolean isClientError(int status) {
    return status >= 400 && status < 500 && status != 408 && status != 429;
}

// in getPrice()'s retry loop
} catch (PriceClientException e) {
    circuitBreaker.release(permit); // not the service's fault → no retry, no failure
    throw e;
} catch (Exception e) {
    lastFailure = e;
}

src/main/java/org/designprinciple/CircuitBreaker.java

/**
 * Give the permit back without recording a success or failure, for calls whose
 * outcome says nothing about the service's health (e.g. HTTP 4xx).
 * Frees the HALF_OPEN trial so the next caller can probe; otherwise does nothing.
 */
public synchronized void release(Permit permit) {
    if (isStale(permit)) {
        return;
    }
    if (permit.type == Permission.TRIAL) {
        halfOpenRequestInProgress = false;
    }
}
  • Why release() is needed: if a 4xx happened during the half-open trial and the permit was simply dropped, the trial flag would stay set and the breaker would be stuck in HALF_OPEN for good. That's the same problem the old allowRequest() had.
  • Decision: a 404 during the trial frees the trial; it doesn't close the circuit. A 404 does show the server is reachable, so treating it as a success would also be reasonable. "Doesn't affect the breaker" was chosen because that's what the review asked for.

4. A missing price fails straight away

Before: if the JSON had no price or the body was empty, a null was cached and stored in CartItem. The NullPointerException only appeared later in getTotalPrice().

src/main/java/org/service/SimplePriceService.java (in fetchPrice())

PriceResponse response;
try (BufferedReader reader =
             new BufferedReader(new InputStreamReader(conn.getInputStream()))) {
    response = gson.fromJson(reader, PriceResponse.class);
}

// Fail here rather than letting a null price surface later in the cart
if (response == null || response.getPrice() == null) {
    throw new RuntimeException("Price missing in response for product: " + product);
}
if (response.getPrice().signum() < 0) {
    throw new RuntimeException("Negative price in response for product: " + product);
}
return response.getPrice();

src/main/java/org/util/Cart.java (second safeguard, for any PriceProvider)

BigDecimal price = priceProvider.getPrice(product);
if (price == null) {
    throw new IllegalStateException("No price returned for product: " + product);
}
lruCache.put(product, price);
  • Decision: a missing or negative price counts as a service failure, so it's retried and counts towards the breaker. If the API keeps returning bad data, retrying won't help, but a 200 response with a broken body could also be a temporary server-side problem.

5. Product names are checked before they go into the URL

Before: product was joined into the URL as-is, so something like "../foo" changed the path.

src/main/java/org/service/SimplePriceService.java

// Product names are used as a URL path segment, so only allow safe characters
private static final Pattern VALID_PRODUCT = Pattern.compile("[A-Za-z0-9_-]+");

// first thing in getPrice(), before asking the breaker for a permit
if (product == null || !VALID_PRODUCT.matcher(product).matches()) {
    throw new IllegalArgumentException("Invalid product name: " + product);
}

Invalid names such as ../foo, corn flakes or cornflakes?x=1 fail before any HTTP call, so they never affect the breaker.

7. Totals round up

Before: subtotal, tax and total used RoundingMode.HALF_UP. The brief says "Totals should be rounded up where required", so they now use RoundingMode.UP.

src/main/java/org/util/Cart.java

// The spec says "Totals should be rounded up where required", so round UP (not HALF_UP)
public BigDecimal getTax() {
    return getSubtotal()
            .multiply(new BigDecimal("0.125"))
            .setScale(2, RoundingMode.UP);
}

The spec's sample gives the same answer either way (15.02 × 0.125 = 1.8775 → 1.88). The difference shows with a subtotal of 0.10: the tax is 0.0125, which HALF_UP turned into 0.01 and rounding up turns into 0.02.

Context

  • In the current app this edge case can't happen. Cart is single-threaded and ShoppingCartApp makes calls one after another, so nothing is in flight when the state changes. The fix matters once the breaker is shared between threads.
  • For comparison: as far as I know, Resilience4j records late results against the breaker's current state rather than the state they started in. Libraries often accept this edge case. If you discuss it in a review or interview, the point to make is that you know it exists, why it happens, and how a generation number closes it.
